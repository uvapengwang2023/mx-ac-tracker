# Prime 空调参数采集整理工具化方案

生成时间：2026-05-28 10:08:18  
适用场景：对 Prime 及其他墨西哥电商/品牌官网空调产品资料进行重复采集、整理、校验和输出。

## 1. 结论

本次流程中最值得工具化的不是单一“识别表格”动作，而是一条可复用的半自动采集流水线：

1. 来源链接管理与文件下载。
2. URL 时间信息解析。
3. PDF/图片文本与表格抽取。
4. 空调参数字段标准化。
5. 型号、功能卖点、来源口径拆分。
6. 异常值检测与人工复核清单。
7. Excel/CSV/MD 标准文件生成。
8. 过程经验沉淀为 Codex Skill。

建议先做脚本和 Skill，再考虑网站。脚本适合快速复用，Skill 适合固化工作方法，网站适合团队长期批量录入。

## 2. 可工具化环节与具体方案

### 2.1 来源链接管理与下载

适合工具形态：脚本。

输入：

- 产品资料 URL 列表。
- 可选：历史汇总文件路径。
- 可选：品牌名、项目名、输出目录。

输出：

- 下载后的原始 PDF/图片文件。
- `sources_manifest.json` 来源清单。
- 每个文件的下载状态、文件大小、内容类型、采集时间。

具体方案：

- 编写 `scripts/download_sources.py` 或 `scripts/download_sources.mjs`。
- 对 URL 做去重，避免重复下载。
- 根据 URL 文件名保存到 `data/<brand>/source_files/`。
- 对下载失败、重定向、非 PDF/图片类型做状态记录。
- 生成来源清单，供后续脚本统一读取。

建议字段：

| 字段 | 说明 |
|---|---|
| source_id | 来源唯一编号 |
| url | 原始链接 |
| local_path | 本地文件路径 |
| content_type | 文件类型 |
| downloaded_at | 下载时间 |
| status | success / failed / skipped |
| note | 备注 |

优先级：高。这个环节稳定、通用、风险低。

### 2.2 URL 时间信息解析

适合工具形态：脚本函数 + 字段规则。

输入：

- 来源 URL。

输出：

- `site_upload_year`
- `site_upload_month`
- `site_upload_ym`
- `url_time_source`

具体方案：

- 识别 WordPress 常见路径：`/uploads/YYYY/MM/`。
- 本次资料中：
  - `https://prime.com.mx/wp-content/uploads/2023/10/ELITE-2-1.jpg` 提取为 `2023-10`。
  - `https://prime.com.mx/wp-content/uploads/2025/06/*.pdf` 提取为 `2025-06`。
- 如果 URL 没有时间片段，不强行推断，保留空值，并在来源说明里标注“URL 未提供上传年月”。

建议函数：

```python
def extract_upload_ym(url: str) -> dict:
    """Extract /uploads/YYYY/MM/ from a product URL."""
```

输出字段应写入：

- 核心参数表。
- 扩展参数表。
- 功能卖点表。
- 来源与口径表。

优先级：高。用户已明确该信息是产品录入网站的时间。

### 2.3 PDF/图片文本与表格抽取

适合工具形态：脚本 + 人工复核流程。

输入：

- 下载后的 PDF/图片。
- 来源清单。

输出：

- 每个来源的原始文本。
- 表格候选结果。
- 页面渲染图。
- 低置信度字段清单。

具体方案：

- PDF：
  - 使用 `pypdf`、`pdfplumber` 或 `PyMuPDF` 提取文本。
  - 对参数表页面渲染为 PNG，便于视觉复核。
  - 对表格结构不稳定的 PDF，保留“文本抽取 + 视觉复核”双轨。
- 图片：
  - 使用 OCR 或视觉模型识别表格。
  - 识别后必须保留原图链接和截图证据。
- 输出中保留原文，不直接只存规范值。

建议目录：

```text
data/<brand>/extracted/
  source_text/
  rendered_pages/
  table_candidates/
  review_flags/
```

优先级：高。但不能完全无人值守，因为 PDF 源文件可能存在明显异常。

### 2.4 空调参数字段标准化

适合工具形态：Schema + 字段字典 + 脚本。

输入：

- 抽取出的原始字段。

输出：

- 标准化后的空调参数记录。

具体方案：

- 建立 `schemas/aircon_specs.schema.json`。
- 建立 `dictionaries/aircon_field_map.yml`，把西语/英语/中文字段映射到统一字段。
- 保留两类字段：
  - 原文字段：如 `refrigerant_raw`、`power_supply_raw`。
  - 规范字段：如 `refrigerant_type`、`voltage_norm_v`。

核心字段建议：

| 标准字段 | 中文含义 |
|---|---|
| brand | 品牌 |
| series | 系列 |
| model_key | 型号/表头 |
| capacity_ton | 匹数 |
| cooling_capacity_btu_h | 制冷量 |
| heating_capacity_btu_h | 制热量 |
| power_supply | 电源 |
| voltage_norm_v | 规范电压 |
| cooling_power_w | 制冷功率 |
| eer | EER |
| seer | SEER/REEE |
| refrigerant_type | 冷媒类型 |
| evaporator_dimensions_mm | 蒸发器尺寸 |
| condenser_dimensions_mm | 冷凝器尺寸 |
| indoor_noise_db | 室内噪音 |
| outdoor_noise_db | 室外噪音 |
| source_url | 来源 URL |
| site_upload_ym | 网站录入年月 |
| source_note | 来源备注 |

优先级：高。字段标准化是后续跨品牌、跨批次汇总的基础。

### 2.5 型号映射拆分

适合工具形态：脚本规则 + 异常检测。

输入：

- 参数表中的型号格。

输出：

- 蒸发器单冷型号。
- 蒸发器冷暖型号。
- 冷凝器单冷型号。
- 冷凝器冷暖型号。
- 型号异常说明。

具体方案：

- 识别常见前缀：
  - `EMPRC`：蒸发器单冷。
  - `EMPRN`：蒸发器冷暖。
  - `CMPRC`：冷凝器单冷。
  - `CMPRN`：冷凝器冷暖。
- 对表头型号和型号格不一致做标记。
- 例如本次 `TRENDY_3_POPUP.pdf` 中，表头为 `122-T3`，但型号格为 `121-T3`，应进入异常清单。

优先级：中高。型号信息对商品录入非常关键，且容易出错。

### 2.6 功能卖点提取与产品覆盖检查

适合工具形态：Skill 规则 + 脚本校验。

输入：

- 产品系列列表。
- 功能描述文本。
- 来源 URL。

输出：

- 功能卖点表。
- 产品覆盖检查结果。

具体方案：

- 每个产品/系列至少生成一组功能卖点。
- 功能表必须包含：
  - 产品/系列。
  - 功能/卖点。
  - 整理说明。
  - 来源 URL。
  - 网站录入年月。
- 校验“参数表中存在的产品系列”是否都出现在“功能卖点表”中。
- 若缺少产品，自动报错或生成复核提示。

本次应覆盖：

| 产品/系列 | 来源时间 |
|---|---|
| Elite 2 | 2023-10 |
| Elite 4 | 2025-06 |
| Trendy K | 2025-06 |
| Trendy 3 | 2025-06 |

优先级：高。用户已指出遗漏产品的问题，适合纳入强校验。

### 2.7 异常值检测

适合工具形态：规则文件 + 校验脚本。

输入：

- 标准化参数记录。

输出：

- 异常报告。
- Excel 中的备注或异常列。

具体方案：

- 建立 `rules/aircon_validation.yml`。
- 规则分为三类：
  - 范围异常。
  - 一致性异常。
  - 来源异常。

建议规则：

| 规则 | 示例 |
|---|---|
| SEER 合理区间 | 低于 8 或高于 35 需要复核 |
| EER 合理区间 | 低于 2.5 或高于 5 需要复核 |
| 低压/高压合理区间 | 低压大于高压需要复核 |
| 容量与匹数匹配 | 12000 BTU/h 通常约 1 Ton |
| 型号一致性 | 表头型号与型号格后缀不一致时标记 |
| URL 时间缺失 | 无 `/uploads/YYYY/MM/` 时标记为空值来源 |

本次应自动识别的异常：

- `TRENDY_K_POPUP.pdf` 中 `362-K` 的 `SEER=2.2` 疑似异常。
- `TRENDY_K_POPUP.pdf` 中 `低压=50 MPa` 疑似异常。
- `TRENDY_3_POPUP.pdf` 中 `122-T3` 表头与 `121-T3` 型号格不一致。

优先级：高。异常检测能显著减少人工漏看。

### 2.8 Excel/CSV/MD 输出生成

适合工具形态：脚本 + 模板。

输入：

- 标准化参数记录。
- 功能卖点记录。
- 来源清单。
- 异常清单。

输出：

- Excel 汇总文件。
- CSV 文件。
- 整理经验 MD。
- 异常报告 MD。

具体方案：

- 建立固定 workbook 模板。
- 默认 Sheet：
  - `汇总_核心参数`
  - `扩展参数_PDF`
  - `型号映射`
  - `功能卖点`
  - `来源与口径`
  - `异常检查`
- 文件命名规则：
  - `01_<项目名>参数汇总_<timestamp>.xlsx`
  - `02_<项目名>参数汇总_<timestamp>.csv`
  - `03_<项目名>整理经验_<timestamp>.md`
  - `04_<项目名>异常检查_<timestamp>.md`
- 永远新建文件，不覆盖旧文件。

优先级：高。输出格式固定后，后续批次可以直接合并对比。

### 2.9 整理经验沉淀

适合工具形态：Skill。

输入：

- 本次处理日志。
- 异常清单。
- 人工修正点。

输出：

- 经验 MD。
- 可追加到 Skill 的规则建议。

具体方案：

- 每次整理结束后自动生成“经验沉淀”文档。
- 重点记录：
  - 哪些字段容易误读。
  - 哪些 URL 有时间信息。
  - 哪些 PDF 表格结构异常。
  - 哪些规则应该加入下一版校验。

优先级：中高。适合让流程越跑越稳。

## 4. Skill 方案

Skill 名称建议：`aircon-spec-collector`

Skill 目标：

- 用户给出品牌官网、电商页面、PDF 或图片链接后，按统一流程采集空调参数。
- 输出标准化 Excel/CSV/MD。
- 保留来源、录入年月、异常说明和人工复核项。

Skill 核心规则：

1. 必须记录来源 URL 和本地文件。
2. 必须从 URL 中提取网站录入年月，若没有则留空并说明。
3. 必须按标准字段输出核心参数。
4. 必须保留原文值和规范值。
5. 必须生成型号映射表。
6. 必须生成覆盖所有产品/系列的功能卖点表。
7. 必须生成异常检查结果。
8. 必须新建带时间戳文件，不覆盖历史文件。

适合放入 `SKILL.md` 的工作流：

```text
1. 读取用户提供的 URL 和历史文件。
2. 下载所有来源文件。
3. 解析 URL 上传年月。
4. 抽取 PDF/图片文本和表格。
5. 映射为空调标准字段。
6. 识别型号与功能卖点。
7. 执行异常检测。
8. 生成 Excel、CSV、经验 MD、异常 MD。
9. 校验文件结构和关键字段。
10. 向用户返回新文件路径和异常摘要。
```

## 5. 脚本方案

推荐先实现一个总入口：

```bash
python scripts/collect_aircon_specs.py \
  --brand Prime \
  --sources examples/prime_sources.yml \
  --history outputs/previous/prime_elite2_specs.xlsx \
  --output outputs/
```

`prime_sources.yml` 示例：

```yaml
brand: Prime
project_name: Prime空调参数
sources:
  - series: Elite 2
    url: https://prime.com.mx/wp-content/uploads/2023/10/ELITE-2-1.jpg
    type: image
  - series: Elite 4
    url: https://prime.com.mx/wp-content/uploads/2025/06/ELITE_4_POPUP.pdf
    type: pdf
  - series: Trendy K
    url: https://prime.com.mx/wp-content/uploads/2025/06/TRENDY_K_POPUP.pdf
    type: pdf
  - series: Trendy 3
    url: https://prime.com.mx/wp-content/uploads/2025/06/TRENDY_3_POPUP.pdf
    type: pdf
```

脚本输出：

```text
outputs/<brand>_aircon_specs_<timestamp>/
  01_<brand>空调参数汇总_<timestamp>.xlsx
  02_<brand>空调参数汇总_<timestamp>.csv
```

## 6. 网站方案

适合在批量任务增多后建设。

核心页面：

1. 来源导入页：
   - 粘贴 URL。
   - 上传 PDF/图片。
   - 填写品牌、系列、来源说明。

2. 抽取预览页：
   - 左侧显示 PDF/图片渲染页。
   - 右侧显示识别出的表格和字段。
   - 支持人工修改。

3. 异常复核页：
   - 展示 SEER、压力、型号不一致等异常。
   - 支持标记“按源文件保留”或“人工修正”。

4. 导出页：
   - 导出 Excel/CSV/MD。
   - 保存历史版本。
   - 比较不同批次。

适合技术栈：

- 前端：React / Next.js。
- 后端：Python FastAPI。
- 文件处理：PyMuPDF、pdfplumber、Pillow。
- 存储：本地文件或 SQLite。
- 导出：openpyxl / xlsxwriter。

优先级：中。适合多品牌、多人员协作时建设。

## 7. AI API 与普通脚本的边界

工具化时应明确区分“确定性处理”和“认知型处理”。确定性处理优先用普通脚本、规则和模板完成；只有在需要理解图片、复杂版式、自然语言卖点、跨字段判断时，才调用 AI API。

这样设计有几个好处：

- 降低成本：下载、命名、字段校验等不消耗 AI token。
- 提高稳定性：确定性逻辑可测试、可复现。
- 方便审计：AI 参与的环节单独留下输入、输出、置信度和人工确认记录。
- 便于扩展：后续可以替换 OCR、视觉模型或大语言模型，而不影响主流程。

### 7.1 不需要调用 AI API 的环节

这些环节适合用普通脚本、规则、模板或数据库处理：

| 环节 | 原因 | 推荐工具 |
|---|---|---|
| 来源 URL 去重 | 字符串和哈希处理即可 | Python / Node.js |
| 文件下载 | 标准 HTTP 请求 | requests / fetch |
| 文件命名与目录管理 | 确定性规则 | Python pathlib / Node fs |
| URL 上传年月提取 | 正则可稳定识别 `/uploads/YYYY/MM/` | regex |
| 文件类型识别 | MIME、扩展名、文件头可判断 | filetype / mimetypes |
| 采集时间记录 | 系统时间即可 | datetime |
| Excel/CSV/MD 输出 | 模板化生成 | openpyxl / xlsxwriter / artifact-tool |
| 字段单位换算 | 规则明确 | 普通脚本 |
| 型号前缀拆分 | 规则明确，如 EMPRC/EMPRN/CMPRC/CMPRN | regex |
| 产品覆盖校验 | 集合比对即可 | 普通脚本 |
| 异常值规则检测 | 阈值和一致性规则即可 | YAML 规则 + 脚本 |
| 历史文件版本管理 | 文件系统和 manifest 即可 | 普通脚本 |

判断原则：

- 输入结构清楚。
- 规则可写成 if/else、正则或配置文件。
- 输出不依赖语义理解。
- 错误可以通过单元测试发现。

### 7.2 建议调用 AI API 的环节

这些环节不一定必须调用 AI，但调用 AI 会明显提升效率，尤其是资料来源复杂、版式不统一时：

| 环节 | AI 价值 | 推荐方式 |
|---|---|---|
| 图片表格识别 | 图片中的表格 OCR 容易错位，视觉模型可辅助理解行列关系 | 视觉模型 + 人工复核 |
| PDF 复杂表格还原 | PDF 文本抽取顺序可能混乱，AI 可辅助恢复表格结构 | 文本抽取结果 + 页面截图一起输入 |
| 功能卖点提取 | 卖点常以自然语言、图标、段落出现，AI 更适合归纳 | LLM 摘取 + 保留来源 |
| 西语字段语义映射 | 不同资料字段名称不一致，AI 可辅助映射到标准字段 | LLM + 字段字典约束 |
| 来源口径说明生成 | 需要把异常、补充来源、保留原则写成人可读说明 | LLM 草拟 + 程序插入 |
| 经验总结生成 | 需要从本次异常和人工修正中提炼流程经验 | LLM 总结 |
| 跨字段疑似异常解释 | 例如判断 `SEER=2.2` 更像源文件异常还是低效产品 | 规则先标记，AI 辅助解释 |

判断原则：

- 输入是图片、复杂版式或自然语言。
- 需要归纳、翻译、理解上下文。
- 规则难以覆盖所有版式变化。
- 输出仍要保留证据和人工确认入口。

### 7.3 高度建议调用 AI API 的环节

以下环节若完全不用 AI，会明显增加人工成本：

| 环节 | 原因 | 控制方式 |
|---|---|---|
| 扫描图/图片型参数表识别 | 纯脚本无法稳定理解图片表格结构 | 输出置信度和原图坐标 |
| 图标型功能卖点识别 | 卖点可能只有图标加少量西语文案 | 要求 AI 输出来源片段 |
| 多语言卖点归纳 | 西语文案需要转成中文录入口径 | 保留西语原文和中文整理说明 |
| 非标准 PDF 表格结构恢复 | 文本抽取可能把列顺序打散 | 页面截图与文本双输入 |
| 异常项解释说明 | 需要判断是 OCR 错误、源文件异常还是口径差异 | 规则触发后再调用 AI |

这些环节不建议让 AI 直接写最终结果，而应采用“AI 提议 + 程序校验 + 人工复核”的方式。

### 7.4 可选调用 AI API 的环节

这些环节可以不用 AI，但在批量处理或要求更高可读性时可以使用：

| 环节 | 不用 AI 的做法 | 使用 AI 的收益 |
|---|---|---|
| 字段字典扩展 | 人工维护 YAML | 自动发现新字段并建议映射 |
| 异常报告文案 | 模板生成 | 说明更自然，便于业务人员阅读 |
| 产品系列命名规范 | 正则和人工配置 | 自动识别近似系列名 |
| 历史批次差异摘要 | 脚本列出差异 | AI 解释变化重点 |
| 商品录入文案草稿 | 从字段模板拼接 | 更适合电商页面展示 |

### 7.5 建议的 AI 调用架构

建议把 AI 调用封装成独立模块，不要散落在主流程里。

推荐结构：

```text
scripts/
  collect_aircon_specs.py
  ai/
    extract_image_table.py
    normalize_feature_points.py
    explain_anomalies.py
    summarize_experience.py
  rules/
    deterministic_validators.py
```

主流程应先执行普通脚本：

```text
下载文件 -> URL 时间解析 -> 文本/PDF 基础抽取 -> 字段初步映射 -> 规则校验
```

只有在以下条件触发时才调用 AI：

```text
图片型来源
PDF 表格抽取失败
字段无法映射
功能卖点缺失
异常规则触发且需要解释
需要生成经验总结
```

### 7.6 AI 输出必须保留的审计信息

每次调用 AI API，建议保存：

| 字段 | 说明 |
|---|---|
| ai_task_id | AI 任务编号 |
| model | 使用的模型 |
| input_file | 输入文件或截图 |
| input_excerpt | 输入文本片段 |
| prompt_version | 提示词版本 |
| output_json | AI 原始结构化输出 |
| confidence | 置信度或自评 |
| needs_review | 是否需要人工复核 |
| reviewed_by | 人工复核人 |
| reviewed_at | 复核时间 |
| final_decision | 最终采用、修正或拒绝 |

这可以避免后续不知道某个字段是脚本确定得出的，还是 AI 判断得出的。

### 7.7 本项目各环节建议分类

| 环节 | 是否需要 AI API | 建议 |
|---|---|---|
| 来源下载 | 不需要 | 脚本完成 |
| URL 时间解析 | 不需要 | 正则完成 |
| PDF 文本抽取 | 通常不需要 | 先用 PDF 工具 |
| PDF 表格结构恢复 | 视情况需要 | 复杂版式再调用 AI |
| 图片参数表识别 | 高度建议 | 用视觉模型辅助 |
| 字段标准化 | 部分需要 | 规则优先，无法映射再调用 AI |
| 型号拆分 | 不需要 | 正则和规则完成 |
| 功能卖点提取 | 建议 | LLM 提取和归纳 |
| 产品覆盖校验 | 不需要 | 集合校验 |
| 异常值检测 | 不需要 | 规则引擎完成 |
| 异常原因解释 | 建议 | AI 辅助生成说明 |
| Excel/CSV 输出 | 不需要 | 模板生成 |
| 整理经验 MD | 建议 | AI 总结，人工确认 |
| Skill 编写 | 建议 | AI 起草，人审定 |
| 网站实现 | 不需要 | 常规开发即可 |

### 7.8 成本控制建议

1. 默认不开 AI，只在触发条件出现时调用。
2. 同一来源文件的 OCR/视觉结果缓存，避免重复调用。
3. AI 输入尽量裁剪到相关页面、相关表格、相关段落。
4. 输出强制 JSON，减少后处理成本。
5. 关键字段必须经过规则校验，不能直接信任 AI 输出。
6. 异常字段保留“按源文件保留”和“人工修正”两种状态。
