# Prime 空调参数采集整理工具化方案 v2

生成时间：2026-05-28 11:06:09  
版本定位：基于 23 个型号实战后的完整修订版  
对应数据文件：`outputs/prime_aircon_specs_20260528_103702/01_Prime空调参数汇总_20260528_103702.xlsx`  
适用对象：Codex Skill、自动化脚本、内部网站、低成本执行型 AI、人工复核人员。

## 1. 修订背景

早期方案已经明确了空调参数采集整理可以工具化，并区分了普通脚本与 AI API 的职责。但在后续 23 个型号整理过程中，又暴露出更具体的问题：

1. 同一品牌不同资料形态差异很大：图片、简版图片、完整图片、PDF 功能页、PDF 参数页。
2. URL 中的网站录入年月必须和 EXIF/PDF 元数据时间分开保存。
3. 有些来源只给简版参数，不能推断型号代码。
4. PDF 文本抽取会打散表格列，必须渲染页面核对。
5. 有些源文件存在明显异常值，不能自动修正，只能按源保留并提示复核。
6. PDF 中会出现单位不一致，例如表头写 KW，但数值明显是 W。
7. 功能卖点不能靠想象补，需要有来源文案或明确参数证据。
8. 后续如果交给低成本 AI 或脚本执行，必须提供严格的字段、流程、异常和验收规格。
9. 冷媒充注量不能沿用源文件单位，规范字段必须统一为 kg。
10. 室内机/室外机尺寸不能只保留一个尺寸字段，必须区分裸机尺寸和包装箱尺寸。
11. 若手册把单冷机型和冷暖机型的尺寸分成两行，必须按机型版本拆分，不允许合并。
12. 普通 OCR 不应作为 PDF 参数表主流程；PDF 有文本层时，应优先使用带坐标的文本/表格抽取，OCR 只作为扫描件或图片源兜底。

本 v2 方案的目标，是把“工具化思路”升级成“可开发、可测试、可交接、可复用”的实施规格。

## 2. 总体目标

建立一套空调产品资料采集整理工具链。用户输入一组图片、PDF 或页面 URL，系统输出标准化 Excel/CSV/MD，并保留来源、网站录入年月、原文字段、规范字段、异常检查和人工复核记录。

目标不是完全无人值守，而是半自动流水线：

```text
脚本负责确定性处理
AI 负责视觉和语义不确定处理
人工负责最终复核和异常决策
```

最终交付应支持：

1. 批量下载来源文件。
2. 自动解析 URL 上传年月。
3. 自动提取 PDF 文本和渲染页面。
4. 辅助识别图片/PDF 表格。
5. 映射到统一空调字段。
6. 拆分型号映射。
7. 提取功能卖点。
8. 运行异常规则。
9. 生成 Excel、CSV、经验 MD、异常 MD。
10. 记录 AI 调用和人工复核审计信息。

Manifest 必填字段：

| 字段 | 必填 | 说明 |

## 7. URL 时间解析规则

URL 时间字段是用户明确要求保存的“产品信息录入到网站的时间”。因此必须单独字段化。

规则：

1. 匹配 `/uploads/YYYY/MM/`。
2. 输出 `site_upload_ym = YYYY-MM`。
3. 不使用 EXIF/PDF 元数据覆盖该字段。
4. URL 无时间时留空，并在来源说明中写明。
5. 若 URL 时间与元数据时间不同，两者都保存，主时间仍为 URL。

示例：

| URL | site_upload_ym | metadata_time | 处理 |
|---|---|---|---|
| `/uploads/2025/11/BRIGHT_3_POPUP.jpg` | 2025-11 | EXIF 2025-10 | 主时间用 2025-11 |
| `/uploads/2026/05/FICHA_V3_compressed.pdf` | 2026-05 | CreationDate 2026-04 | 主时间用 2026-05 |

函数规格：

```python
def extract_upload_ym(url: str) -> dict:
    """
    Return:
    {
      "site_upload_year": 2025,
      "site_upload_month": 6,
      "site_upload_ym": "2025-06",
      "url_time_source": "wordpress_upload_path"
    }
    """
```

## 8. 标准数据模型

### 8.1 核心参数模型

核心参数用于业务录入和跨批次汇总。字段要稳定，不因来源缺失而删除。

```json
{
  "brand": "Prime",
  "series": "Bright 3",
  "model_key": "121-B3",
  "capacity_label": "12K",
  "capacity_ton": 1,
  "cooling_capacity_btu_h": 12000,
  "heating_capacity_btu_h": 12000,
  "power_supply": "110-120V/60Hz",
  "voltage_norm_v": 115,
  "cooling_power_w": 1250,
  "cooling_current_a": 11.1,
  "eer": null,
  "seer": 18.25,
  "hspf": 8.6,
  "refrigerant_raw": "R32",
  "refrigerant_type": "R32",
  "refrigerant_charge_raw": "590g",
  "refrigerant_charge_unit_raw": "g",
  "refrigerant_charge_kg": 0.59,
  "indoor_unit_dimensions_raw": "805*197*270",
  "indoor_package_dimensions_raw": "864*265*332",
  "outdoor_unit_dimensions_raw": "660*530*250",
  "outdoor_package_dimensions_raw": "768×575×338",
  "dimension_order_raw": "ancho x prof x alto",
  "source_url": "https://prime.com.mx/wp-content/uploads/2025/11/BRIGHT_3_POPUP.jpg",
  "site_upload_ym": "2025-11",
  "source_note": "来源图未显示净重/毛重字段；保留为空。"
}
```

核心字段分组：

| 分组 | 字段 |
|---|---|
| 基础 | brand, series, model_key, capacity_label, capacity_ton |
| 能力 | cooling_capacity_btu_h, heating_capacity_btu_h |
| 电气 | power_supply, voltage_norm_v, cooling_power_w, cooling_current_a, max_input_w, max_current_a |
| 能效 | eer, seer, hspf, energy_saving_pct |
| 冷媒 | refrigerant_raw, refrigerant_type, refrigerant_charge_raw, refrigerant_charge_unit_raw, refrigerant_charge_kg |
| 尺寸重量 | indoor_unit_dimensions_raw, indoor_package_dimensions_raw, outdoor_unit_dimensions_raw, outdoor_package_dimensions_raw, indoor_unit_width_mm/depth_mm/height_mm, indoor_package_width_mm/depth_mm/height_mm, outdoor_unit_width_mm/depth_mm/height_mm, outdoor_package_width_mm/depth_mm/height_mm, evaporator_net_kg, condenser_net_kg |
| 噪音风量 | indoor_noise_db, outdoor_noise_db, indoor_airflow_m3h |
| 管路 | liquid_pipe_in, gas_pipe_in |
| 型号 | evap_cool_only_model, evap_heat_cool_model, cond_cool_only_model, cond_heat_cool_model |
| 来源审计 | source_file, source_url, site_upload_ym, metadata_time, source_note |

冷媒单位转换规则：

| 源单位 | 规范处理 |
|---|---|
| `g` / `gramos` | 除以 1000，写入 `refrigerant_charge_kg` |
| `kg` / `Kg` / `KGS` | 直接写入 `refrigerant_charge_kg` |
| 表头单位为 `g`，单元格只有数字 | 按表头单位转换 |
| 原文形如 `R32/500g` | 拆出 `refrigerant_type=R32`、`refrigerant_charge_kg=0.5` |
| 只有冷媒类型，没有充注量 | 充注量留空，并标记 `refrigerant_charge_missing` |

尺寸字段规则：

1. 室内机和室外机必须分开。
2. 裸机尺寸和包装箱尺寸必须分开。
3. `ancho x prof x alto`、`ancho x alto x fondo` 等原始顺序必须保留，不允许只按三个数字硬拆。
4. 最终展示可使用 `宽×深×高 mm`，但底层必须保留原文、拆分值和原表顺序。
5. 如果单冷/冷暖尺寸分行，增加 `mode_variant = solo_frio / frio_calor / common`，不允许合并。

## 9. 字段规范化规则

### 9.1 小数

西语小数逗号转为小数点：

| 原文 | 规范 |
|---|---:|
| `18,25` | 18.25 |
| `6,44` | 6.44 |
| `46,77` | 46.77 |

带范围的值不强拆：

| 原文 | 处理 |
|---|---|
| `9.1(2.0-11)` | 字符串保留 |
| `3520(1000-4100)` | 原文保留到扩展表 |

### 9.2 冷媒

冷媒类型和充注量必须拆开，并统一充注量单位为 kg。

| 原文 | refrigerant_type | refrigerant_charge_raw | refrigerant_charge_unit_raw | refrigerant_charge_kg |
|---|---|---|---|---:|
| R410A | R410A | 空 | 空 | 空 |
| R410a/2010g | R410A | 2010g | g | 2.01 |
| R32/500g | R32 | 500g | g | 0.5 |
| 0.65 kg | 空 | 0.65 kg | kg | 0.65 |
| R32 | R32 | 空 | 空 | 空 |

如果只有冷媒类型没有充注量，`refrigerant_charge_kg` 留空，并在异常/复核字段中标记 `refrigerant_charge_missing`。

### 9.3 容量

常用容量映射：

| 标识 | Ton | BTU/h |
|---|---:|---:|
| 12K | 1 | 12000 |
| 18K | 1.5 | 18000 |
| 24K | 2 | 24000 |
| 36K | 3 | 36000 |

如果来源表中直接给 BTU/h，则优先使用来源值。  
如果 PDF 只给 W，但型号标题是 12K/18K/24K，可以核心表按容量标识写 BTU/h，同时扩展表保留 W 原文。

### 9.4 单位冲突

出现单位冲突时：

1. 不自动静默修正。
2. 核心表采用统一业务口径。
3. 扩展表保留原文。
4. 异常检查说明原因。

Vantage 3 案例：

| 字段 | 源文件 | 本次处理 |
|---|---|---|
| Consumo de Energía Nominal | 单位栏显示 KW，数值 1040/1200/1400/2100 | 核心按 W 录入 |
| Capacidad Nominal | W | 核心按 12K/18K/24K 转 BTU/h，扩展保留 W |

### 9.5 尺寸

尺寸必须双轨保存：既保留原文字符串，也输出规范拆分字段。

必须区分：

- 室内机裸机尺寸。
- 室内机包装箱尺寸。
- 室外机裸机尺寸。
- 室外机包装箱尺寸。

保留原文字符串：

```text
805*197*270
830×270×190
827*299*200
```

同时输出：

- `dimension_order_raw`：例如 `Ancho x Profundidad x Alto`、`ancho x alto x fondo`。
- `*_width_mm`
- `*_depth_mm`
- `*_height_mm`

注意：

- 不同来源标注顺序不一致，因此必须先识别 `dimension_order_raw`，再拆成宽/深/高。
- `profundidad` 和 `fondo` 都可表示深度。
- 如果源表把单冷和冷暖尺寸分行，必须用 `mode_variant` 拆开，不允许合并。
- 裸机尺寸应小于包装尺寸，反向时进入异常检查。

## 10. 型号映射规则

Prime 型号前缀：

| 前缀 | 设备 | 版本 |
|---|---|---|
| EMPRC | 蒸发器 | Solo Frío |
| EMPRN | 蒸发器 | Frío/Calor |
| CMPRC | 冷凝器 | Solo Frío |
| CMPRN | 冷凝器 | Frío/Calor |

映射输出字段：

- evap_cool_only_model
- evap_heat_cool_model
- cond_cool_only_model
- cond_heat_cool_model

规则：

1. 来源明确给出时才填。
2. 简版图没有型号代码时不推断。
3. 表头和型号格不一致时进入异常检查。
4. 型号后缀应与系列一致，例如 `-B3`、`-R3`、`-V3`、`-U3`。

Bright 1 案例：

```text
来源只显示容量、电压、能效、尺寸、重量。
未显示 EMPRC/EMPRN/CMPRC/CMPRN。
因此型号映射全部留空。
```

## 11. 来源类型处理流程

### 11.1 图片完整参数表

适用：A1 Advanced、R3 Advanced、Bright 3。

流程：

1. 下载图片。
2. 查看完整图。
3. 必要时裁剪参数表区域并放大。
4. 识别列标题和型号行。
5. 按列录入每个型号。
6. 提取功能卖点。
7. 运行异常规则。

AI 使用建议：

- 图片表格识别高度建议调用视觉模型。
- 不建议整页 OCR 后直接入表；应先定位表格区域，再按行列切块识别。
- 冷媒、尺寸、重量、电流、电压等短数字字段必须人工或规则复核。

### 11.2 图片简版参数表

适用：Bright 1。

流程：

1. 只录入图中明确字段。
2. 缺失字段留空。
3. 不推断型号代码。
4. 在来源口径和异常检查中说明“简版图限制”。

### 11.3 PDF 功能页 + 参数页

适用：Vantage 3、Ultra 3。

流程：

1. 下载 PDF。
2. 读取 PDF 页数。
3. 第 1 页提取功能卖点。
4. 判断 PDF 是否有文本层。
5. 有文本层时，优先用 `pdfplumber` 或 `PyMuPDF` 提取带坐标的 words、lines 和表格边界。
6. 通过字段标签锚点、表格线、x/y 聚类恢复行列关系。
7. 第 2 页渲染成图片，作为视觉复核和单元格截图证据。
8. 只有在扫描版或图片型 PDF 中，才使用 OCR 或视觉模型识别。
9. 按恢复后的列录入参数。
10. 异常项写入异常检查。

重要经验：

- PDF 文本抽取可能把列顺序打散。
- `pypdf` 可证明文本层存在，但线性文本顺序会打散表格，不适合作为最终表格解析。
- 参数页必须渲染图片核对，并保留关键单元格证据。
- 功能页适合 AI 摘取卖点。
- 参数页适合脚本优先还原表格，AI/视觉模型辅助处理不确定单元格，最终要有规则校验。
- OCR 是兜底，不是主流程。

| 环节 | 工具 |
|---|---|

### 12.2 建议 AI 的环节

| 环节 | 原因 |
|---|---|
| 图片表格识别 | OCR 容易错位，视觉模型更适合 |
| PDF 复杂表格恢复 | 文本抽取顺序会打散 |

| 异常解释 | 需要判断源文件异常还是单位差异 |
| 经验总结 | 需要归纳流程 |

### 12.3 AI 调用原则

1. 先脚本，后 AI。
2. 能规则化就不用 AI。
3. AI 输出必须 JSON。
4. AI 输出必须带来源证据。
5. AI 输出不能直接覆盖源值。
6. 异常值必须保留“按源文件保留”选项。
7. 人工复核决策必须可追踪。

      - capacity_ton_min: 3

## 17. 验收标准

每次运行必须满足：

1. 输出目录为新目录，未覆盖旧文件。
2. Excel 文件存在且可通过压缩包完整性测试。
3. CSV 文件存在且行数与核心表一致。
4. 核心表记录数等于来源中型号/容量数量。
5. 每个系列都出现在功能卖点表。
6. 每个来源都出现在来源与口径表。
7. URL 中有 `/uploads/YYYY/MM/` 的来源必须有 `site_upload_ym`。
8. 异常检查 Sheet 存在且包含所有规则触发项。
9. Bright 1 等简版来源不应被自动推断型号。
10. PDF 的 W 原文应保留在扩展表。
11. AI 输出如被采用，必须有审计记录。
12. 不存在公式错误。

## 24. 最终结论

这类空调参数采集整理工作完全值得工具化，但不应追求一次性全自动。最佳形态是：

```text
确定性脚本 + 视觉/语言 AI + 规则校验 + 人工复核 + 标准化导出
```

23 个型号的整理经验表明，真正影响质量的不是“能不能识别文字”，而是：

1. 是否保留来源与时间。
2. 是否区分原文和规范值。
3. 是否避免推断。
4. 是否把异常值显式暴露。
5. 是否能让下一位执行者复现同样结果。

因此，v2 方案必须被视为实施规格，而不是普通经验文档。后续开发脚本、Skill 或网站时，应以本文件作为基准。
